# Content Guidelines
Version: 1.0
Project: LowKeyDevs

---

# Purpose

This document defines the writing standards for all content published on LowKeyDevs.

Every piece of content should help users solve a problem as quickly as possible.

Content exists to support the tool, not replace it.

Users visit LowKeyDevs to use tools first and read second.

---

# Core Philosophy

Every sentence should answer at least one of these questions.

- What is this?
- Why should I use it?
- How does it work?
- When should I use it?
- What should I avoid?
- What happens behind the scenes?

If a sentence answers none of these, it probably shouldn't exist.

---

# Writing Principles

Content should be

- Helpful
- Accurate
- Concise
- Technical when necessary
- Beginner friendly
- Easy to scan

Never write simply to increase word count.

Every paragraph must provide new information.

---

# Writing Style

Write like a knowledgeable engineer explaining something clearly.

Avoid sounding like a marketer.

Avoid sounding like an academic paper.

Avoid sounding like AI.

The tone should be

Professional

Friendly

Calm

Confident

Practical

---

# Audience

Write for

Developers

Students

Designers

Professionals

Casual users

Assume curiosity, not expertise.

Explain technical concepts without talking down to readers.

---

# Reading Level

Target

Grade 7–9 readability.

Use short sentences.

Prefer familiar words.

Avoid unnecessary jargon.

Explain technical terms the first time they appear.

---

# Tool First

The interactive tool is always the primary focus.

Never hide the tool below long introductions.

Users should be able to use the tool immediately.

Supporting content belongs below the tool.

---

# Content Structure

Every tool page should follow this order.

1. Hero

2. Interactive Tool

3. Introduction

4. Features

5. How It Works

6. Use Cases

7. Step-by-Step Guide

8. Privacy

9. Limitations

10. FAQ

11. Related Tools

12. Summary

---

# Introductions

The introduction should

Explain what the tool does.

Mention the primary keyword naturally.

Set expectations.

Avoid unnecessary history.

Maximum

120 words.

---

# Explanations

Explain concepts from first principles whenever possible.

Do not simply describe what a button does.

Explain why it exists.

Help users understand the underlying idea.

---

# Features

Features should describe benefits, not just capabilities.

Poor

Supports PNG.

Better

Convert PNG images directly in your browser without uploading files.

---

# Step-by-Step Guides

Keep instructions short.

One action per step.

Assume the user wants the fastest path.

Avoid unnecessary explanations inside steps.

---

# Use Cases

Provide realistic examples.

Good examples

Compressing screenshots

Formatting API responses

Creating secure passwords

Converting image formats

Avoid unrealistic or overly broad examples.

---

# Examples

Include examples whenever possible.

Examples improve understanding more than long explanations.

Prefer

Before / After

Input / Output

Real scenarios

---

# FAQs

Answer questions users actually search for.

Good

Is this tool free?

Does it work offline?

Is my data uploaded?

Can I use it on mobile?

How accurate is it?

Avoid fake or unnecessary FAQs.

---

# Privacy

Every tool page should explain

Whether files leave the browser

Whether data is stored

Whether internet access is required

Never make false privacy claims.

---

# Limitations

Be honest.

Explain what the tool cannot do.

Users trust transparent limitations.

---

# Comparisons

When appropriate

Compare with alternatives objectively.

Focus on

Speed

Privacy

Convenience

Compatibility

Never attack competitors.

---

# Internal Links

Naturally recommend related tools.

Only link when relevant.

Avoid excessive linking.

Recommended

3–8 related tools.

---

# External References

Link only to trustworthy sources.

Examples

MDN

Google

Mozilla

W3C

WHATWG

RFC documents

Avoid low-quality references.

---

# Keyword Usage

Keywords should feel natural.

Do not repeat the same phrase excessively.

Use synonyms.

Use semantic variations.

Write for humans first.

---

# Formatting

Prefer

Short paragraphs

Bullet lists

Tables

Examples

Avoid

Large walls of text.

---

# Lists

Lists should

Contain related items.

Be easy to scan.

Stay concise.

Avoid lists longer than 10 items unless necessary.

---

# Tables

Use tables for

Comparisons

Supported formats

Measurements

Specifications

Compatibility

Avoid tables that contain only one column.

---

# Images

Only include images that improve understanding.

Every image must

Have descriptive ALT text.

Support the surrounding explanation.

Never use decorative images without purpose.

---

# Code Examples

Use code blocks.

Keep examples short.

Explain why the example matters.

Prefer real examples over placeholders.

---

# Technical Accuracy

Never guess.

Never fabricate.

Never invent standards.

Never invent browser behavior.

If uncertain

State the uncertainty clearly.

---

# AI Writing Rules

Never use phrases like

"In today's digital world..."

"Nowadays..."

"This amazing tool..."

"Powerful solution..."

"Revolutionary..."

"Game-changing..."

"The ultimate..."

Avoid filler.

Avoid repetitive transitions.

Avoid obvious statements.

Avoid empty conclusions.

---

# Brand Voice

LowKeyDevs is

Minimal

Fast

Practical

Honest

Technical

Respect the reader's time.

Avoid unnecessary excitement.

---

# Quality Checklist

Before publishing, verify

✓ The tool appears before content.

✓ The introduction explains the tool.

✓ Every section adds value.

✓ Examples are realistic.

✓ Privacy is explained.

✓ Limitations are honest.

✓ FAQs are useful.

✓ Internal links are relevant.

✓ No repeated paragraphs.

✓ No keyword stuffing.

✓ No AI clichés.

---

# Absolute Rules

Never write content only to reach a word count.

Never exaggerate.

Never invent facts.

Never repeat the same information.

Never waste the user's time.

Never prioritize SEO over usefulness.

---

# Final Principle

Every paragraph should make the user better informed.

If removing a paragraph does not reduce the page's usefulness, that paragraph should not exist.
